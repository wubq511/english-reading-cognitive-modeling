description: Investigate a question against high-trust primary sources and capture a provenance-aware Markdown asset in this research repository. Literature questions run a documented search — local library, open scholarly APIs (Crossref/OpenAlex/Semantic Scholar/arXiv/PubMed/ERIC), web search, a web-AI deep-search round, and a human-tasks register for gated databases like CNKI — then a two-stage screen, staged reading, and a human review before any ticket closes. Use for literature, standards, API facts, or a Wayfinder research decision.
---

Run the research in a background Agent only when the user and current platform policy permit delegation. Otherwise perform the same bounded investigation in the current session; delegation is an optimization, not a correctness requirement.

An LLM summary — yours, a chatbot's, or a search engine's AI overview — is not evidence. Every consequential claim traces to a held or fetched primary source. The local library is itself the product of earlier searches; answering from local holdings alone silently inherits those searches' blind spots, so every literature question runs a fresh, documented search before reading.

Work only the user can do (environment setup, gated-database queries, paywalled acquisition) lives in `reports/research/human-tasks/` — the standing register: one file per ticket, a cross-ticket `setup.md`, and a README that owns the registration rules. The moment any step below produces human work, register it in the matching file and point the user at the file and section in chat — never bury human tasks deep inside a long asset. Register files are written in Chinese for the research members; bibliographic entries keep their original language.

## Process

1. **Preflight, owner, setup.** Run `scripts/bootstrap` and identify the canonical owner before writing. Standalone research usually belongs in `reports/research/`; a result that changes a current project claim updates that claim's owner under `reports/` instead of creating a competing note. If `scripts/sources doctor` fails, stop work that depends on the missing full texts. Then check setup before searching: if `OPENALEX_API_KEY` or `S2_API_KEY` is unset, register it in `reports/research/human-tasks/setup.md`, name it to the user, and pause until the user confirms the keys or says to proceed without them — proceeding without is a recorded search boundary, because anonymous quotas on this machine's shared proxy are unreliable.

2. **Frame the search protocol.** Convert the question into explicit queries (several phrasings, including domain synonyms), target indexes, inclusion/exclusion criteria (population, task, method, date range), and what a decisive contrary finding would look like. Record this protocol verbatim in the asset's method/search boundary: a reviewer must see what was searched, when, with what coverage, and what was rejected. Decide explicitly whether the question needs a Chinese-database round (CNKI/Wanfang/CQVIP, always a gated human channel): run it only when the question genuinely depends on domestic content — Chinese-context populations or programs, domestic assessment systems, Chinese-language instruments or journals; skip it when the question's research base is international and Chinese literature is expected to be low-value. Either decision is recorded in the boundary with a one-line rationale. Completion: the protocol is specific enough that a second agent could rerun it.

3. **Local stock-take.** Search `sources/catalog.yaml` and `reports/` for sources already held; they are the first evidence base, and re-acquiring a held source is waste. Completion: every held source relevant to the protocol is listed with its stable ID.

4. **Open-web search.** Query the free scholarly APIs from the shell; together they cover international literature plus major Chinese journals:
   - Crossref: `https://api.crossref.org/works?query=<q>&rows=20&mailto=<project-email>` — metadata and DOIs; the `mailto` keeps you in the polite pool
   - ERIC (education research — first-class for this project): `https://api.ies.ed.gov/eric/?search=<q>&format=json&rows=20` — free, no key; many records link free full text at `files.eric.ed.gov/fulltext/ED######.pdf`, which is directly acquirable
   - OpenAlex: `https://api.openalex.org/works?search=<q>` — abstracts (inverted index) and `best_oa_location` for open PDFs. Anonymous access shares a daily budget per exit IP — this machine rides a shared proxy, so the budget is often burned by others (429 "Insufficient budget", resets midnight UTC). If the env var `OPENALEX_API_KEY` exists, pass it as `api_key=`; if the budget is exhausted, record the boundary and lean on the other indexes — do not burn the day retrying
   - Semantic Scholar: `https://api.semanticscholar.org/graph/v1/paper/search?query=<q>&fields=title,abstract,openAccessPdf,year,venue` — rate-limited without a key; use header `x-api-key: $S2_API_KEY` when the env var exists, otherwise space requests ≥1/s and skip on repeated 429
   - arXiv: `https://export.arxiv.org/api/query?search_query=<q>`
   - PubMed: `https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi?db=pubmed&term=<q>`
   Setup (once per machine): the free OpenAlex and Semantic Scholar keys live as the env vars above; registration is a human task tracked in `reports/research/human-tasks/setup.md`. Keys never enter the repo or logs.
   **Web-AI deep-search round (default for literature questions).** Web AI chats (ChatGPT/Kimi/Gemini, especially deep-research modes) ride search backends the free APIs miss — JS-rendered pages, publisher landing pages, multi-hop iterative search, Chinese-language literature. Build the copy-paste prompt from `assets/deep-search-prompt-template.md`, filling its slots from the protocol; the user pastes it into the chat of their choice and relays the raw answer back. You then verify and screen it like any other channel — confirm each item's bibliographic reality via Crossref/ERIC/DOI resolution before it enters the queue, and check the AI's prose claims about a paper against the paper itself (or a fetched abstract), never quoting them as the paper's own words. Verification level, not the channel, decides what enters the evidence table. Record the round in the boundary: date, items returned, how many survived verification.
   Use `WebSearch` as a first-class discovery channel alongside the APIs — it reaches what structured indexes miss: theses, institutional and OECD-style reports, standards drafts, Chinese-language sources without DOIs — and it reliably surfaces canonical papers with direct PDF links. Run several natural-language phrasings, then chase the citations it surfaces to their DOI pages. Use `FetchURL` for standards bodies, official documentation, and publisher landing pages; for public pages that bot-wall curl (403), the user's browser (or the local playwright skill) renders them fine — public content only, never login or paywall circumvention. Chase citations for every on-point seed: Semantic Scholar `/paper/{DOI}/references` (backward) and `/citations` (forward) — one strong seed often outperforms ten query variants. The proxy is intermittent: curl always with `--retry 5 --retry-all-errors --retry-delay 2`; repeated total failure means the line is down — record the failed index as a boundary, compensate through the remaining channels, and move its expected coverage into the human queue rather than dropping it. Google Scholar blocks automation (HTTP 403): record it as a search boundary and route its coverage through the human queue instead of scraping. Completion: per query, a dated hit list with its index; per seed, a citation-chase record; per blocked channel, a boundary entry plus a user task.

5. **Two-stage screen.** Stage 1 — judge each hit by title/abstract/metadata against the protocol's inclusion criteria. Dedupe by study, not by record: a preprint and its journal version are one study — cite the archival version. Keep one-line exclusion reasons for near-misses; the screen record is part of provenance. Stage 2 — for screened-in items, read whatever full text or rich metadata is reachable to confirm fit and assign a quality tier. Record a PRISMA-style flow table in the asset's method section: per channel, identified → deduped → screened → included. Quality grading: peer-reviewed primary research outranks preprints, reports, and metadata-only records; manipulative designs outrank correlational ones for causal claims; population/task fit to the question is itself a quality axis. How much to include is governed by coverage × saturation, not by a target count: every cell of the question's load-bearing claim matrix needs at least one direct source; load-bearing claims need two to three sources across independent populations or designs; a branch is saturated when two consecutive dated queries or citation chases surface no new on-point study — record the saturation and stop. Where included syntheses overlap (several meta-analyses pooling the same primary studies), note the overlap and never double-count pooled evidence. Completion: every screened-in hit assigned to exactly one acquisition route below.

6. **Acquisition triage — hand off human work immediately after screening, before any deep reading.**
   - **Open access** — a public PDF exists (OpenAlex `best_oa_location`, arXiv, PubMed Central, publisher OA page). Register the source in `sources/catalog.yaml` and `sources/checksums.sha256`, then `scripts/sources sync` performs eligible downloads itself.
   - **Gated** — login/subscription channels (CNKI, Wanfang, CQVIP, Web of Science, Scopus, paywalled publisher full text) are the human route. Access failure never removes a source from consideration; it converts into a user task. Register each item in the ticket's own file under `reports/research/human-tasks/` (one file per ticket, named like `wayfinder-5-ui-instrument-effects.md`; create it from the register README's rules if absent): exact title/authors/venue/year/DOI, why the question needs it, the suggested channel with a clickable DOI/publisher link, and — when the database's own search is also gated — the exact queries for the user to run there. Then point the user at the file in chat with a compact checklist — one action per item with a direct link. Screen whatever the user brings back and name which items to fetch in full text; PDFs go to `tmp/pdfs/`, then verify identity/version/rights/SHA, register them, and run `scripts/sources inbox` and `scripts/sources doctor`. When handing off, tell the user plainly what blocked you and which channels. Open a tracking ticket only when the user asks; for a solo workflow the register plus chat checklist is the faster surface. `sources/README.md` owns these mechanics — follow it rather than paraphrasing it here.
   - **Unreachable** — mark `ABSTRACT-ONLY` or `UNKNOWN` and keep the exclusion record.
   Never guess a DOI, license, or version, and never route around a paywall. Third-party originals stay out of public Git regardless of route.

7. **Reading, staged by what it feeds.** Reading that improves the search — on-point seeds for citation chasing, terminology refinement — may begin immediately. Reading that feeds conclusions waits until the acquisition queue clears, because conclusions must rest on all located evidence, not on the accessible subset. While the queue is non-empty, label every finding INTERIM; INTERIM findings may steer the next search round but cannot close a research ticket. For local full-text claims, require `scripts/sources doctor` and cite stable source ID plus page/section/table/figure. Mark `ABSTRACT-ONLY`, `UNKNOWN`, or inaccessible evidence honestly. Separate source statements from `PROJECT-INFERENCE`; record applicability, alternatives, contrary evidence, and what remains unresolved.

8. **Write one Markdown asset** with question, method/search boundary (protocol, coverage, flow table, blind spots), evidence table with quality tiers, findings, limitations, acquisition queue pointer, decision implications, and exact citations. The asset is written in Chinese prose (analysis, claims, limitations, decision implications); English stays only where untranslatable — bibliographic titles, quoted source text, query strings, source IDs, and term anchors. It opens with a Chinese `结论速览` section (core conclusions, how they were produced, open residuals). Index it in `reports/research/README.md`.

9. **Human review before close.** Before anything goes to GitHub, brief the user in chat, in Chinese (the research members' working language). The briefing carries: (a) a work list — what was actually done (channels searched with dates, sources acquired, screen outcomes, what was read); (b) headline findings; (c) a file guide naming, per output, which file and section holds it and one line on what it says, so the reviewer can navigate without excavating; (d) open residuals — unread queue items, boundaries, INTERIM labels. The human research member is the reviewer of record — a resolution they have not seen is not a resolution. Post the resolution comment (link the asset, don't paste the report) and close the ticket only after the user's sign-off. If the search located relevant sources that remain unread (acquisition queue not yet cleared), say so plainly: the ticket stays open by default, and closing earlier is the user's explicit call. Run proportionate link/source/repository verification. Research is complete when the artifact, its search record, and its citations are reviewable — not when the prose sounds decisive.
