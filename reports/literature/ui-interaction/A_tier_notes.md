## 一、Process-related User Interaction Logs: State of the Art, Reference Model, and Object-Centric Implementation

> 📄 **期刊**：*Information Systems*（2024）· **DOI**：10.1016/j.is.2024.102386
>

> UI要记录哪一些？怎么处理关系？怎么分层？到什么程度（粒度）？
>
- 聚焦UI日志的标准化和统一：包括记录的形式到导入使用的形式
- 提取共性，对分歧点进行灵活化处理，供使用者自行选择
- Object centric 注意处理好不同的对象之间的关系，不预设case notion
- 对于特定的场景，要考虑其合适的Action抽象粒度
- 4 层 UI 层级按需使用

    **四层树状层级**：

    | **层级** | **是什么** | **例子** |
    | --- | --- | --- |
    | **UI element**（最底层） | 原子级界面控件，可带状态 | 按钮、文本框、下拉框、复选框、滑块；状态如"已填内容的文本框""置灰的按钮" |
    | **UI group** | 一组元素的组合，可嵌套 | 登录掩码（用户名+密码+登录按钮）、Excel 的工作表（sheet）、一个窗体面板 |
    | **Application** | 单个程序实例 | 浏览器、SAP 客户端；有些操作直接作用于应用本身（"撤销"、快捷键） |
    | **System**（最顶层） | 应用运行所在的系统 | Windows；系统级操作如 Ctrl+Alt+Del 打开任务管理器 |

## 三、User Behavior Mining: A Research Agenda

> 📄 **期刊**：*Business & Information Systems Engineering*（2024）· **DOI**：10.1007/s12599-023-00848-1
>

> 用户交互日志分析挖掘
>
- 文章提出把分析业务流程的成熟技术（过程挖掘）用到这些日志上，从而研究用户行为，并给出了一套完整的研究框架（数据→技术→目标→理论）和未来研究方向。
- 论文把"活动"定义为 **目标元素 + 动作类型**。迁移到答题平台：

| **字段** | **你的版本** | **例子** |
| --- | --- | --- |
| Case ID | 作答编号 | A20260805-001 |
| 时间戳 | 发生时刻 | 14:02:31 |
| 目标元素 | 题目 ID / 控件 | 题-07 / 选项B / 提交按钮 |
| 动作类型 | 操作 | 进入题目 / 选中选项 / 修改答案 / 提交 / 跳过 / 上一题 |
| 值（可选） | 输入内容 | 答案：C |
| 附加属性 | 学生 ID、每题用时 | 学生 42 |
- UI日志的**高粒度（High Granularity）**

    原始日志记录的是底层操作（鼠标点击、键盘输入），噪音大，**必须先抽象成有意义的活动再分析：**`Ctrl+V` 和 `右键→粘贴` 明明是一回事，却被记成两个不同活动。反过来，很多底层事件对分析是**噪音**（比如你在研究 ERP 的使用，却去查了下邮件）。


> **所以分析 UI 日志的第一件事永远是：抽象（abstraction）**——把细粒度事件提升到有意义的层次，同时识别和剔除噪音。
粒度太细必须抽象，但**抽象程度取决于目标。**
>

## 四、A Grammar-Based Approach for Applying Visualization Taxonomies to Interaction Logs

> 📄 **期刊**：*Computer Graphics Forum*（2022）· **DOI**：10.1111/cgf.14557
>

> 将低层动作信息串联成有意义的用户行为
>
- **原始日志是"零碎的动作"，分类法提供的是"有意义的类别"。**

    一段原始日志可能是这样的：

    | **时间** | **用户** | **动作** |
    | --- | --- | --- |
    | 10:01:02 | U1 | mouseover_from_list（鼠标悬停在列表项上） |
    | 10:01:05 | U1 | change_attribute_distribution（改了分布图的属性） |
    | 10:01:08 | U1 | filter_changed（改了过滤条件） |
    | 10:01:11 | U1 | mouseout（鼠标移出） |

    这些记录非常"低层"（low-level）。研究者想回答的是"用户在做什么任务、有什么意图"，而日志只给了"动作"。

    于是需要一层**抽象（abstraction）**：把"动作"翻译成"类别"。

    - `mouseover_from_list` → 属于"select（选择）"类
    - `change_attribute_distribution` → 属于"aggregate（聚合/重新计算）"类
    - `filter_changed` → 属于"filter（过滤）"类

    翻译完之后，日志就从"一串动作"变成了"一串有语义的类别"，比如：

    ```
    select → aggregate → filter → ...
    ```

    这就能谈"用户行为"了。

- **人和软件交互的方式，和语言有结构上的相似性。**
    - 单个交互 → 像单词；
    - 交互的顺序规律 → 像语法；
    - 一组交互表达的分析意图 → 像句子表达的意思。

    | **语言** | **交互日志分析** |
    | --- | --- |
    | 单词 | **交互（interaction）**——一次点击、一次悬停 |
    | 终结符 | 低层分类法里的类别（filter、select、navigate……） |
    | 非终结符 | 高层分类法里的模式名（overview、drill-down、scan……） |
    | 产生式规则 | 用终结符的正则表达式定义模式 |
    | 句子 | 一段有意义的交互模式/任务序列 |

    语言学早就用文法（语法）来建模"单词如何组成有意义的句子"，那我们可以用同样的形式语言工具，建模"交互如何组成有意义的分析模式"。

- 分类细粒度太粗会导致信息丢失

## 五、Trace Clustering for User Behavior Mining

> 📄 **会议**：*ECIS*（2022）· **原文**：ECIS2022 全文 PDF
>

> 轨迹聚类
>
- **发现规则覆盖不到的行为模式（探索）**

人写的规则只能识别预设的行为；聚类不预设类别，直接看行为自然分成几群。不限制簇数的方法能找出规则没覆盖的细粒度行为（比如某种未知的求助方式或交互循环），发现后再抽样本人工核验，能补充行为字典。

- **验证行为变量字典是否真实（交叉验证）**

行为变量是依据文献和直觉设计的，未必抓住了真实结构。用变量做嵌入再聚类，与人工标注的标签比对一致性（可用 ARI）：一致说明变量设计可信，可以放心做监督模型；不一致说明变量有冗余或漏维度，应回到定义阶段修订，不要急着训练。

- **个体差异的分层分析**

把学生按行为模式聚成几群（如快速试错型、看提示慢推型、大量回访型），再比较各群在反馈利用改善率、任务完成度、成绩上是否有系统差异。分组标签只能描述行为模式，不能自动命名心理状态，因果需另做实验。

- **消融实验的工具（导航该不该留、属性该不该进）**

用聚类的成败当"试纸"判断数据特性：同一批日志分别按结果视角和交互视角聚类，比较质量与可读性。交互视角明显崩掉说明导航是噪声；没崩甚至更好说明教育导航携带任务语义。上下文属性同样可以这样对比。

## 八、Unsupervised Clickstream Clustering for User Behavior Analysis

> 📄 **会议**：*CHI 2016*（Proceedings of the 2016 CHI Conference on Human Factors in Computing Systems）· **DOI**：10.1145/2858036.2858107
>

> 通过非监督聚类分析用户点击流数据，对用户行为/习惯进行类别划分
>
- 能否借鉴用于不同学生学习行为/习惯的分析和类别划分
- 特点：
    - 第一，它必须在规模庞大且充满噪声的点击流数据集上表现良好、可扩展。
    - 第二，系统应当能够捕获此前未知的用户行为，即在没有预先定义类别或标签的情况下捕获行为。这一点至关重要，因为用户常常以出人意料的方式使用热门服务，而能否顺应这些行为可能决定一个服务的长期存亡。
    - 第三，系统应当具有交互性，通过直观、可理解的方式呈现检测到的行为，帮助他人理解用户行为。与之相对，现有工具通常把用户模型当作完成分类任务的"**黑盒**"，几乎不解释用户的行为方式及其原因。
- 原理：

    从高层来看，我们的系统利用点击流之间的相似度度量来构建相似度图，从而捕获用户之间的行为模式。图的边刻画用户点击流之间的相似距离，簇则代表行为相似的用户群体。我们采用层次聚类方法来检测最流行的行为模式，并利用迭代式特征剪枝技术，在每一层簇划分后移除主导特征的影响。最终得到一棵行为簇的层级树：越上层的簇代表越普遍的用户行为模式，越下层的簇则进一步识别出在关键行为模式上存在差异的更小群体。我们还可以利用卡方统计量找出可用于对行为簇进行分类和打标签的统计特征。

- 事件体系**依赖具体服务**，换 App/场景 需要设计定义不同的click events

> For other services, specific events will depend on the service functionalities. For example, Wikipedia, News or Q&A sites [28] might extract events based on the category or topic of the pages. Ecommerce web sites can define user events based on the functionality of the clickable links or product categories. Crowdsourcing sites can define click events based on the crowdsourcing workflow.
>
- **"日志 → 行为模型"的完整管道模板**：原始事件 → 时间离散化 → n-gram 特征 → 相似度 → 聚类 → 可解释簇
- **创新点：**

    代特征剪枝与分裂式层次聚类的递归耦合，使得大规模点击流聚类在无监督条件下同时获得层次结构和自解释性（每簇自动附带判别特征作为语义依据），让点击流聚类能做到无监督 + 可解释 + 层次结构 + 大规模四个条件同时成立。


## 九、Recovering Reasoning Processes from User Interactions

> 📄 **期刊**：*IEEE Computer Graphics and Applications*（2009）· **DOI**：10.1109/MCG.2009.49
>

> 仅凭交互日志，能恢复分析师多少推理过程（策略、方法、发现）？（假设：与设计良好的 VA 工具交互时，大量推理过程嵌入交互中，可通过人工检查日志恢复）
>
- 日志记录**能产生视觉变化的事件**（如鼠标移动高亮 heatmap 关键词 → 带时间戳事件），而非每个鼠标/按键

> **日志记录粒度的取舍（最值得抄的一条）**：它证明了「记什么事件」是决定下游推断成败的设计决策——低层全量记录噪声太大，**记「对数据有意义的可视化变化事件」信噪比最高**。
>
- 前提：推理过程本来就隐含在交互里，研究者的任务是把它挖出来，而不是凭空推断。意味着，需要对答题交互进行埋点设计。

> 也就是说，一个人是怎么想的，会通过他点哪里、看哪里、先后看什么**流露**在操作序列里。
>
- 我们当前的方法很可能只适用于**高度交互的可视化系统**（因为只有这类系统里，分析师的意图才大量体现在操作上）。「交互性」与「视觉表征」各自在多大程度上影响推理的恢复，仍是一个悬而未决的问题。
- 通过人工检查交互日志，可以恢复分析师相当大比例的推理过程（发现 79%、方法 60%、策略 60%）；但**纯粹依赖视觉画面才能看出的推理（如时间序列图中的尖峰）几乎无法从日志恢复**，这是该方法最明确的边界。
- **双视角分析工具的思路**：**「过程视角（时间轴回放）+ 目标视角（维度聚合）」双视图互补**是经过实证有效（编码者实测靠它破解乱序列）的设计，比单视图更利于人读懂日志。

## 十一、Mining System-User Interaction Traces for Use Case Models

> 📄 **会议**：*IWPC 2002*（10th International Workshop on Program Comprehension）· **DOI**：10.1109/WPC.2002.1021305
>

> **从"用户怎么用系统"的记录中，反推出"系统是干什么用的"。**
>
- **用例**是统一建模语言（UML，软件工程的标准画图语言）里的核心概念：描述"某个外部角色（人、另一个系统或硬件）通过和系统交互，完成一个有价值的目标"的完整故事。例如：读者通过图书馆系统检索一本书，就是一个用例。
**用例模型** = 一个系统所有重要用例的集合，本质上是"这套系统到底为用户提供哪些功能"的功能清单。
- **频率/支持度（frequency/support）**：某个模式在全部数据里出现的次数。次数不够多的模式被认为是"偶然噪音"，不是真任务。
- **极大模式（maximal pattern）**：如果模式 A 是模式 B 的一部分、且 B 出现次数和 A 一样多，那 A 就是"多余的子模式"，会被删掉。留下的"不能再长"的模式叫极大模式。这样结果更精简、更容易看懂。
- **行程长度编码（Run-Length Encoding, RLE）**

    一种经典压缩法：把连续重复的内容"压缩"。比如 `AAAAABBB` 记成 `5A3B`。本文用它处理"用户连续翻了好几页"这种情况——连续 6 次出现 6 号屏幕，就记成 `(6)6`，意思是"6 号屏幕出现 6 次"。这样既保留信息，又不会让无意义的重复干扰模式匹配。

- 使用**知识发现**（knowledge discovery，数据挖掘的学名，指从数据中提取有用知识）和**模式搜索**算法，在轨迹中搜索频繁出现的模式
- 通过挖掘轨迹中反复出现的屏幕模式，我们的方法提取出界面的实际、一致的使用方式，这些使用方式很可能对应着遗留应用的用例。
快照轨迹 → LeNDI 分类成屏幕 → 挖掘反复屏幕模式 → 提取一致使用方式 → 对应用例。
- 适用边界（自己承认的局限）：**只适用于"成熟稳定 + 界面信息丰富"的系统**；批处理或界面贫瘠的系统信息量不够，做不了。
- 流程

    ```jsx
    遗留系统（旧、无好源码）想换新界面
       │
       │ 必须知道"这系统被用来干什么"
       │
       ▼
    录下用户交互轨迹（屏幕快照序列 + 用户按键）
       │
       │ LeNDI 把相似快照归类 → 轨迹变成"屏幕编号序列"
       │
       ▼
    序列模式挖掘（滑动窗口 + 长度×频率评分）
       │
       ▼
    找出反复出现的屏幕模式（≈ 用户频繁执行的任务）
       │
       │ 专家人工核验 + 补上"每个屏幕能输入/输出什么"的语义
       │
       ▼
    形成用例模型 → 用 Mathaino 为每个任务生成新的网页界面
    ```

## 十二、Automatic Macro Mining from Interaction Traces at Scale

> 📄 **会议**：*CHI 2024*（Proceedings of the CHI Conference on Human Factors in Computing Systems）· **DOI**：10.1145/3613904.3642074 · **arXiv**：2310.07023
>

> 从大量交互轨迹（随机爬取 + 用户策展）自动提取语义有意义、可执行、带自然语言描述的宏
>
- 作者主张 LLM 具备移动 UI 与日常任务的常识，可"审视"UI 提取任务。定位：不是"行为推断"（不建模个体用户行为、不推断意图/策略/求助），而是**任务模板发现 + 动作合成**
- 把屏幕转换成一段"简化 HTML"塞进提示里，然后问 LLM 三个问题（这就是第 3.2 节的三个子步骤）：
    1. **任务发现**：问"这个界面上的用户能做什么？"（"What can a user do with this UI?"）→ LLM 返回任务列表，比如"创建提醒 - 编辑提醒标题 - 设置提醒时间…"
    2. **动作锚定**：问"要完成'创建提醒'，下一步该点哪个元素？只回答数字 id，或 None。"→ LLM 回答"1"（对应保存按钮）。
    3. **参数查找**：问"除了点这个按钮，用户还需要填哪些信息？"→ LLM 回答"标题、日期"，再逐参数问"标题在哪里输入？"→ LLM 回答元素 id。
- 分工：**LLM 只管局部语义、图算法做全局拼接**
- 流程

```jsx
海量交互轨迹（随机爬取 + 用户真实操作）
        │
        ▼
┌──────────────────────── 阶段一：Task Extraction（LLM 逐屏）────────────────────────┐
│  对每条轨迹的每个屏幕，把屏幕转成"简化 HTML"喂给 LLM，连续问 3 个问题：              │
│  ① 任务发现：这屏幕上用户能做什么？→ 得到候选任务描述列表                            │
│  ② 动作锚定：要完成这个任务，下一步该点哪个元素？（只许回答元素 id 或 None）        │
│  ③ 参数查找：除了点击，用户还要填哪些信息？分别填在哪？                              │
└──────────────────────────────────────────────────────────────────────────────────────┘
        │  产出：一堆"带描述 + 一串动作 + 参数"的候选宏（含大量冗余前缀）
        ▼
┌──────────────────────── 阶段二：Action Merging（确定性图算法，不用 LLM）────────────┐
│  每个 app 建一张"动作交互图"→ 跨轨迹合并相同动作 → BFS 找最短路径 → 用最短路径      │
│  替换候选宏里的冗余动作序列（平均缩短约一半：RICO -43.6%，Rehearsal -54.7%）        │
└──────────────────────────────────────────────────────────────────────────────────────┘
        │  产出：最终宏集合 M = {(d 描述, A_opt 最优动作集, {p} 参数)}
        ▼
┌──────────────────────── 附加模块：Macro Replayer（自动执行）────────────────────────┐
│  adb 控制安卓模拟器，按"模糊匹配"找元素点击，某步失败就跳到后面能匹配的步（容错）   │
│  → 60 个宏里 76.7% 成功回放到最终屏幕                                               │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

- 可能可以用于分析学生答题交互轨迹，分析抽象出常见的高层事

## 十三、 Recognizing Task-level Events from User Interaction Data

> 📄 **期刊**：*Information Systems*（2024）· **DOI**：10.1016/j.is.2024.102404
>

> 提出**无监督**方法把交互数据变换为满足过程挖掘两个要求的 task-level events：识别任务及其类型 + 通过对象实例建立任务与过程执行的关系
>
- 论文从头到尾反复用的例子：一位用户在处理客户订单，系统记录了 16 条交互（u1–u16，见下表简化版）：

| **事件** | **动作** | **应用** | **元素** | **标签(Label)** | **值(Value)** |
| --- | --- | --- | --- | --- | --- |
| u1 | click | Mail | list | Order | — |
| u2–u4 | input/click | Chrome | field/button | Login / Password / ok | — |
| u5 | click | Chrome | button | **Create order** | **O007501** |
| u6 | input | Chrome | field | Search | Pete Miller |
| u7 | input | Chrome | field | Customer | C0075 |
| u8 | click | Chrome | button | Save order | O007501 |
| u9 | click | Mail | list | Change request | — |
| u10 | input | Chrome | field | Customer | C0081 |
| u11 | click | Chrome | button | Edit order | O008102 |
| u12–u13 | input/click | Chrome | field/button | Quantity=4 / Save order | O008102 |
| u14–u16 | input/click | Chrome | field/button | Edit order / Quantity=5 / Save order | O008102 |

**人类一眼能看出**：u1–u8 是"创建订单 O007501"这一个任务；u9–u16 是"编辑订单 O008102"另一个任务。LLM能否也能够直接分析出结果？？：（具体效果对比可进行实测）

> **1. 规模与流式（最硬的差距）**
>
>
> 真实工作日的交互日志是几十万条事件，而 LLM 的上下文窗口是有限的（就算 200K tokens，也只能装几万条事件）。你想让它看全全局信息（论文里共现矩阵、控制流计数这类**跨任务积累的统计**）就装不下；分块喂又割裂了全局上下文。而论文方法的整个设计就是**增量式的**：每来一个事件处理一次，内存占全量数据的 **不到 1%**，可以无限跑。LLM 天然是"整段输入 → 整段输出"，不是流式。
>
> **2. 精确的边界判定（LLM 的软肋）**
>
> 任务切分是要**精确到每个事件归属哪个任务**的。LLM 擅长"讲一个合理的分段故事"，但它对"第 47 个事件到底属于上一个任务还是下一个任务"这种精确判断，会给出**自信但可能错**的答案——而且它不会告诉你它哪里不确定。论文方法每个边界都有可验证的明确条件（上下文相似度、数据值重叠、overhead、确定性），错了能定位是哪个条件错。**"可解释、可定位"在工程和科研里是刚需，LLM 给不了。**
>
> **3. 对象实例的精确关联**
>
> 任务级事件要求"这个 O007501 精确属于这个任务"。长数字 ID、邮箱、人名，LLM 在长序列里**很容易记错或编造**（幻觉）。这种 ID 级的精确匹配，反而是正则 + 规则最稳的地方。
>
> **4. 可复现性与成本**
>
> - 论文方法跑同样输入 100 次，结果 100 次一样，零成本，本地跑
> - LLM 输出有随机性（即使 temperature=0 也不是逐位确定的），科研/审计场景不可接受；几十万事件全喂 API，成本是天文数字；交互日志还含大量个人信息（邮箱、人名、浏览记录），发给外部 API 有隐私问题——论文原文还专门提到"流式处理可以避免存储含个人信息的低层事件"
>
> **5. 概念漂移与类型一致性**
>
> 论文的 DenStream 能优雅处理"出现新任务类型"：新类型自然形成新簇，老类型不被遗忘。LLM 是"看上下文行事"的：你把 10 个创建订单的任务都叫了"Create order"，第 11 个可能叫"新建订单"——**标签不稳定**。而聚类的类型体系是自洽、一致的。
>
> **6. "任务类型"的语义**
>
> 这里有个微妙点：论文的"类型"是**聚类出来的**（统计上相似的任务归一堆），不是外部定义的真值。LLM 给的是"常识意义上的名字"。两者压根不是一回事。你要的是可复现的、可对比的类型体系（论文的 Rand/Jaccard 指标才能算），LLM 给不了稳定的体系。
>

**把 LLM 用在"理解"和"命名"这两端（它最强），把结构化方法用在"切割"和"精确提取"这两端（它最强）。**

## 十四、Mining Problem-Solving Strategies from HCI Data

>

> 通过观察用户动作学习其问题求解策略
>

```jsx
        ▼

        │
        ▼
⑤ 人工解读：把"有显著差异的组"命名成策略

```

## 十五、Detecting Usability Problems in Mobile Applications on the Basis of Dissimilarity in User Behavior

> 📄 **期刊**：*International Journal of Human-Computer Studies*（2020）· **DOI**：10.1016/j.ijhcs.2019.10.001
>

> 提出在移动应用可用性测试中**基于用户行为相似度/差异度自动检测可用性问题**的方法与工具
>
- 基本假设是：**用户遇到可用性问题时，会以彼此不同的方式与移动应用交互**（也就是说，行为会发生分化——有人这样点，有人那样点）。基于这一思路，我们提出了对用户行为进行**追踪**（tracing，记录用户的每一步操作）、**建模**（modeling，把操作记录转化成可比较的形式）和**比较**（comparing）的方法，用来度量用户行为的相似度（similarity，衡量不同用户的行为有多一致）。
- 流程：

```jsx
┌─ 阶段一：数据采集（Tracing）─────────────────────────────┐
│  安卓手机（装被测 App） ──USB──▶ PC 上的监控工具(UIAutomator) │
│  测试操作员在每场测试开始时，手动输入【参与者ID + 任务ID】       │
│  用户操作时，UIAutomator 实时读取屏幕控件(XML)                │
└──────────────┬────────────────────────────────────────┘
               ▼ 屏幕变化 → 判定是否"新状态"
┌─ 阶段二：行为建模（Modeling）────────────────────────────┐
│  每个用户的操作过程 → 一张【有标号有向图】G=<V,E>              │
│  顶点 = 见过的屏幕；有向边 = 屏幕跳转                         │
│  （边沿实时生成，每个状态还存一张截图）                        │
└──────────────┬────────────────────────────────────────┘
               ▼ 全部用户测完之后
┌─ 阶段三：相似度计算 ────────────────────────────────────┐
│  同一任务内：任意两位用户的行为图 → Jaccard 相似度(0~1)        │
│  两两求完 → 取平均 = 该任务的相似度                           │
└──────────────┬────────────────────────────────────────┘
               ▼ 任务相似度 < 0.6 ?
┌─ 阶段四：问题判定与定位 ─────────────────────────────────┐
│  否 → 判"无问题"                                           │
│  是 → 跑【众数频率算法】找出行为最不一致的那个屏幕 = 问题屏     │
└──────────────┬────────────────────────────────────────┘
               ▼
┌─ 阶段五：报告输出 ──────────────────────────────────────┐
│  HTML 报告：无问题=绿色(显示相似度)，有问题=红色(显示问题屏)    │
└────────────────────────────────────────────────────────┘
```

## 十七、Analyzing the Shifts in Users' Data Focus in Exploratory Visual Analysis

> 📄 **会议**：*IUI 2025*（Proceedings of the 30th International Conference on Intelligent User Interfaces）· **DOI**：10.1145/3708359.3712154
>

> 用户的数据焦点转变策略是否随会话演进？哪类（离线/在线）学习算法最适合建模（用数学模型**预测用户下一步**）这些转变？
>
- **离线**：先攒一大堆历史数据，一次性训练完，之后模型不变；
**在线**：每来一个新交互就**立刻更新模型**。
用户探索行为不断变，理论上"在线"更合适——本文就在验证这个直觉。
- 可视化领域内常用的算法——特别是**贝叶斯学习和 HMM**——在捕捉用户数据焦点动态转变的细微之处时**能力有限**。RL 算法能借助**超参数**（hyperparameters，训练前人为设定的参数，如学习率、折扣因子等）动态适应用户的探索节奏，并在线整合用户的数据兴趣。相比之下，HMM 更适合**无监督**、拥有大量无标签数据的场景，在**嘈杂且数据受限**的环境中表现不佳。
- 任务复杂度和开放性都会提高建模难度，直接影响算法性能。这正**有利于 RL**，因为 RL 擅长在复杂场景中学习决策策略。
- 用户在探索性可视分析中**确实会随探索进程改变自己的数据焦点转变策略**（统计检验证明前后半段显著不同）；在各种候选方法中，**在线强化学习，尤其是改造后的 QLearn-Aligned，建模用户数据焦点转变的效果最好**；开放式任务和复杂任务会让所有模型变难，而简单的基线方法（Momentum、Greedy）仍不可忽视。
- 流程

```jsx
┌─────────────────────────────────────────────────────────────────┐
│ 第1层 数据来源   三个已有用户研究日志（imMens / Tableau / Voyager）  │
│                    （每个日志 = 用户逐次交互的原始记录）              │
└─────────────────────────────────────────────────────────────────┘
                                ↓ 抽象
┌─────────────────────────────────────────────────────────────────┐
│ 第2层 定义三件套  状态state(当前数据焦点) + 动作action(转变策略)      │
│                   + 奖励reward(这次转变值不值得)                    │
└─────────────────────────────────────────────────────────────────┘
                                ↓ 形式化
┌─────────────────────────────────────────────────────────────────┐
│ 第3层 MDP建模     把"用户探索"写成马尔可夫决策过程                   │
│                   （用户=智能体，VES=环境，找洞见=最大化奖励）        │
└─────────────────────────────────────────────────────────────────┘
                                ↓ 统计验证
┌─────────────────────────────────────────────────────────────────┐
│ 第4层 sanity check 用混合效应模型+似然比检验证明：                  │
│                   用户的转变策略在前/后半段确实显著不同               │
└─────────────────────────────────────────────────────────────────┘
                                ↓ 建模
┌─────────────────────────────────────────────────────────────────┐
│ 第5层 参赛算法   RL 4种(Q-learning/SARSA/Reinforce/Actor-Critic)   │
│                 + QLearn-Aligned + 可视化基线(HMM/贝叶斯/SVM…)     │
│                 + 简单启发式(Random/Greedy/WSLS)                  │
└─────────────────────────────────────────────────────────────────┘
                                ↓ 训练与评测
┌─────────────────────────────────────────────────────────────────┐
│ 第6层 两种设定   个体(每人80/20) vs 群体(留一交叉验证)              │
│                 指标 = 动作预测准确率                               │
└─────────────────────────────────────────────────────────────────┘
```

- **"状态-动作-奖励"三件套抽象**——对原始数据进行处理，转化为合适的形式/可学习、可使用的数据

## 十八、A Multi-Modal Dataset for Usability Smell Identification

> 📄 **期刊**：*IEEE Transactions on Affective Computing*（2026）· **DOI**：10.1109/TAFFC.2025.3632675
>

…
